# NBOT V5 G4 RAM-buffered compressed archive recovery, and V4 hypotheses (2026-10-14)

**Deployment mode:** source-only, all NBOT application services stopped. Derived from G1–G7 integration `dc60ecc865ad4dd44418f3204f3ebafc83a7f9f0`. Existing original G1/G2/G3 SQLite and protected rollback archives are untouched. No real or paper orders.

## Storage contract
- G1 remains **zero per-tick SQLite inserts**: the latest quote/trade is coalesced in memory, with 96 finalized closed candles/coin and immutable 5-minute evidence.
- G4's former network capture used `ForwardSourceVault`, with one raw-frame SQLite row for every book/trade/mark-price message. The previous option to process in 64-frame SQL batches did not fix row growth.
- The G4 network capture defaults to `--storage-mode segments`: `SegmentedForwardSource` buffers **at most 2 MiB or 2,048 source receipts** in RAM (whichever first), and a supervisor checkpoint writes any pending data every **5 seconds**. The pending RAM data is turned into lossless gzip-compressed, hash-chained, fsynced, atomically published *segment files*. A small JSON manifest hashes each segment and links to the prior segment. There is **no SQLite per-tick insert** in the capture path.
- Checkpointing still writes data to disk because a full original aggregate-trade sequence is needed to prove which of stop/target was touched first. Source receipt metadata and independent audit must retain raw bytes for scientific provenance. Compression/periodic batching reduces *write operations* and stored volume, not necessarily the number of actual original market updates recorded.
- Crash/reboot/service kill discards **only an uncommitted RAM tail**, bounded by buffer and flush cadence during normal operation. The last confirmed checkpoint survives. On restart, an OPEN previous epoch results in an explicit `ABRUPT_RESTART_HOLD` before a new epoch. Even a clean close does **not** establish uninterrupted cross-restart provenance. Any simulated trade whose required price path crosses that unknown interval must HOLD/censor, never count as a win or loss.
- On interrupted segment publish, orphan or incomplete data, wrong hash, a tampered compression stream, symlink, unsafe permissions, disk quota or RAM bound exceed: fail closed and refuse replay/qualification. Never silently delete or rewrite immutable original source to overcome a quota. Resource overrun is a visible HOLD, not automatic restart.
- Default pilot cap is **256 MiB of compressed archival bytes**, with an explicit, capped sustained operator opt-in. A long-running 50-coin storage budget still requires measured volume, segment rollover and off-host hash/custody archival; the design is NOT a license to run for days unchecked.
- The old `--storage-mode legacy-sqlite` mode is **not the default** and requires explicit `--legacy-per-frame-sqlite-opt-in`; it is **forbidden for sustained acquisition**. Older SQLite evidence remains read-only as historical research input.

## Offline G4 scientific adapter
`verified_ram_vault()` independently verifies the complete compressed sequence (bounded to 100,000 frames and a 128 MiB view), then builds a disposable SQL view in `/dev/shm` (RAM-backed tmpfs on Linux). The earlier **independent original quote and price-path auditors** can inspect this view; it is removed after use. Research can use a segment directory in place of the historic `g4_raw_source.sqlite`. If replay fails/caps out, the candidate population remains HELD. All scored outcomes, after-cost source reviews, G5 champion authorization, G6 challenger authorization and G7 paper/live authority remain separately gated and **unreleased**.

The bounded replay adapter currently proves only limited-window/source-fixture integration. For production sustained 50-coin use, source-window indexing/partitioned on-demand replay, total-disk capacity, full stop/target path completeness and independent real-market provenance still require validation. G4 labels must retain independent exit bid/ask, fees, slippage and actual funding evidence; raw source data alone never equals a fill.

## V4's 24 hypotheses and V5's selection objective
- The frozen V4 `nbot/observation/candidate_setups.py` catalog contains exactly **24 pattern IDs**. V5 `nbot/v5/pattern_adapter.py` validates the catalog checksum, computes **five proxy families + 19 technical rules** from 49–96 fully closed contiguous five-minute bars, records match/no-match/unavailable, and NEVER turns a match directly into a trade. These 24 pattern hypotheses have NOT been deleted.
- In V4's bootstrap source, `V4CandidateScanner.scan()` selected candidates by `(has_matched_tags, -tag_count, market_rank, tie_hash)`; V4's `v4_selection.py` later accepted highest finite LightGBM relative-rank predictions, **not calibrated expected after-cost returns**. Thus a setup can rank #1 even when its expected trade net R is negative. The historical realized loss root cause needs audited historical data, not a label-only inference.
- V5 G1 keeps **every original 50-symbol x two-side directional candidate per 5m event**, including no-pattern or unscorable; G2 captures source proof without survivorship filtering; G3 adds causal BTC/market regime, cross-section and technical context. G4 defines prospective reference stop/target and matures original after-cost economic outcomes with held/censored gaps; G5 chooses a **selective Champion**, comparing net R to no trade and accounting for dependence/multiple hypotheses; G6 trains a separate Challenger only after independent qualified data and review; G7 remains a **locked two-book simulation**, no exchange orders.
- `PATTERN_MATCH` != profit, 24 pattern matches != 24 independent observations, 100 two-sided candidates != 100 fills or outcomes, original WSS receipts != exchange signed/fill grade, simulated profitable tests != qualified economics.
